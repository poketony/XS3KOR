명령 실행 기준: XS3KOR/tools/x30. 일상 작업 순서는 ../README.txt를 참고하세요.
검증 개수와 초기 번역 상태는 구현 당시의 기록이며 현재 결과와 다를 수 있습니다.

X30 SB 빌드 (2026-10-28)

Build_sb.bat를 실행하면 0.X30/cf/kr의 786개 TXT와 0.X30/bat/kr의 전투 TXT 29개를 직접 읽고 각 작업 폴더의 원본 옆에 이름.sb.new 815개를 만듭니다.
기존 번역을 보존한 운영본입니다. 새 번역, 컷신/자막 파이프라인 변경, 외부 ROM 폴더 자동 복사는 하지 않습니다.

실행
- Build_sb.bat: 두 그룹 모두 빌드.
- 0.X30/cf/kr/3.RepackAllStorySb.bat: 필드 그룹 전체. 새로 추가했던 중복 Build_story_sb.bat는 제거.
- 0.X30/cf/kr/4.DragStoryTxt.bat: 드롭 전용. TXT 없이 실행하면 실패하며 전체 빌드를 시작하지 않음.
- 0.X30/bat/kr/1.BattleSbRepack.bat: 기존 이름 복구. 전투 29개 전체 또는 드롭한 TXT만 처리. 중복 Build_battle_sb.bat는 제거.
- TXT 한 개 또는 여러 개를 그룹 BAT에 드롭하면 해당 파일만 직접 읽어 빌드. 파일명이 SB를 선택하며 미등록/다른 그룹/중복 파일은 오류.
- CLI 예(저장소 루트): 0.X30\cf\kr\4.DragStoryTxt.bat 0.X30\cf\kr\8050.txt --check
- 상대 경로는 호출한 폴더 기준. 기본 입력이 없으면 다른 사본을 찾지 않고 실패. XS3_NO_PAUSE=1이면 BAT 대기 생략.
- python -B build_sb.py --check: 전체 검사만 수행. 출력 파일을 저장하지 않음.
- python -B build_sb.py --group cf: 필드 SB만 빌드.
- python -B build_sb.py --group bat: 기존 튜토리얼 5개와 추가 추출한 전투 문구 24개, 총 29개 빌드.
- python -B build_sb.py --asset cf/8050: 한 파일만 빌드.
- python -X utf8 -B -m unittest discover -s tests -p test_sb.py: SB 전용 회귀 테스트.
- 원문 추출: 각 폴더의 .batlock 파일을 사용할 때만 .bat로 바꾸고 끝나면 되돌림. 기존 TXT가 하나라도 있으면 전체 저장을 중단.
- 단일 원문 추출: python tools/x30/build_sb.py --asset cf/8050 --extract. 기존 작업 TXT를 자동 백업/교체하지 않음.
- Python 3.10 이상, 추가 패키지 불필요. tools/x30과 작업 폴더의 SB/TXT/치환표만 필요하며 외부 ROM/XS2/codex-lab에는 의존하지 않음.

원본과 작업 입력
- 원본 입력은 0.X30/cf/kr의 787개와 0.X30/bat/kr의 69개, 총 856개 SB임. 검증용 original/sb 사본은 더 이상 빌드 원본으로 읽지 않음.
- 작업 폴더의 SB와 치환표가 일본판 조사/기준 해시와 일치함을 검사하며, 없거나 다르면 다른 사본으로 대체하지 않고 실패.
- 이중 언어 편집 TXT 815개를 빌드 대상으로 지정. 등록된 TXT가 없으면 오류이며 다른 사본으로 대체하지 않음.
- cf/3810은 문자열이 0개. 전투 SB 40개는 B01/B02/B03/B08 및 --- main --- 등의 내부 라벨만 포함.
  이 41개는 무수정 왕복 시험에 포함하지만 번역 작업/빌드 출력 대상은 아님.
- merged_dialogue_final.txt는 주소별 SB 입력이 아니므로 복사하거나 빌드하지 않음.
- 출처와 원본/치환표/최초 편집 사본의 SHA-256은 sb_sources.json에 기록.
- 작업 입력은 0.X30의 기존 TXT이며 tools/x30/edit에 SB 번역 사본을 두지 않음.
- 이전 정규화 사본은 reference/editor-snapshots-20261024/sb로 보존 이동했으며 회귀 테스트 자료일 뿐 빌드 입력/대체 경로가 아님.

추가한 전투 원문 TXT 24개
- 기존에 TXT가 없던 전투 SB 64개를 모두 구조 기반으로 확인했으며 24개에서 일본어 대사/전투 안내/내부 라벨 280행을 발견.
- 해당 24개를 0.X30/bat/kr에 일본어 원문 그대로 추출. 전체 편집 행은 ASCII 라벨을 포함해 589개이며 자동 번역하지 않음.
- 파일: DOU_B02, DYU_B03, ELS_B01, HAK_B03/05/08/10/11/12, KYO_B02,
  MIK_B01/02/04/06/10/12/13, MUJ_B01, RAV_B02/04, REN_B03, ZDA_B03/04/05.
- --- ... ---와 같은 내부 식별자/디버그 라벨도 원문 보존을 위해 포함됨. 모든 일본어 행을 화면 대사라고 단정하지 말고 실제 대사/안내만 번역할 것.
- 새 TXT는 보스전 중의 문구이며 X31/X32 컷신 자막을 추출하거나 변경한 것이 아님.

복구한 추출 누락
- 기존 도구는 테이블 첫 항목의 상대 주소 0을 종료 표시처럼 취급하여 첫 문자열을 제외했음.
- 첫 문자열이 seg_now 또는 --- main ---인 경우는 내부 표식이므로 새 편집본에서도 제외하고 바이너리는 보존.
- cf의 38개 파일은 첫 문자열이 실제 문장 E.S.に乗りますか？<f>임.
  현재 JPN/KOR TXT에는 이 원문이 [JPN]으로 복원되어 있음.
- 38개 파일명/주소/원문은 sb_sources.json의 restored_first_rows에서 확인 가능.
- 구형 단일 본문 TXT를 입력할 때만 기록된 38개 누락을 원문으로 보완하는 호환 처리가 남아 있음.
- 새 형식에서는 모든 JPN 주소가 있어야 하며 누락/중복은 오류.
- 전환 전 TXT와 도구는 codex-lab/sb-bilingual/backup에 보존했고 migration.json에 SHA-256을 기록함.

TXT 형식
# SB-TEXT: JPN-KOR v1

[0x2fa8]
[JPN]
E.S.に乗りますか？<f>
[KOR]
E.S.에 타겠습니까?<f>

- [JPN]은 검증된 원본이므로 수정하지 않고 [KOR] 한 줄만 편집.
- KOR가 비어 있거나 공백뿐이거나 KOR 구획이 없으면 해당 원본 문자열 바이트를 그대로 유지. 빈 KOR는 문자열 삭제가 아님.
- JPN이 원본 SB와 다르거나 주소가 누락/중복되거나 알 수 없는 주소가 있으면 저장 전에 실패.
- 항목 사이 빈 줄은 서식이며, KOR 본문 앞뒤 공백은 데이터로 보존.
- 게임 문자열에 실제 LF가 필요하면 기존 도구와 같은 [n] 사용.
- 문자 그대로인 \n은 문자 그대로 유지. [n]과 서로 바꾸지 말 것.
- 실제 여러 줄을 본문에 직접 넣으면 오류. [n]으로 표시해야 끝부분 개행도 손실 없이 구분 가능.
- 항목 순서를 바꾸어도 원본 주소로 연결하므로 결과는 같음.
- 내부 표식, 스크립트 식별자, 제어코드, 문장 부호는 임의로 바꾸지 않음.
- 한글 -> 기존 치환표의 대응 한자 -> EUC-JIS-2004 순서 유지.
- 인코딩 불가 문자와 NUL은 오류. 삭제, 물음표 대체, 오류 항목을 건너뛴 저장은 하지 않음.
- 이전 단일 본문 형식은 드롭 호환을 위해 읽을 수 있지만 새 편집본과 새 추출은 JPN/KOR 형식만 사용.

바뀐 알고리즘
- seg_now나 특정 대사를 찾는 휴리스틱 대신 SB 헤더 +0x10의 문자열 섹션 주소 사용.
- 섹션의 +0에 헤더 길이 8, +4에 문자열 수, +8부터 상대 포인터 배열이 있음.
- 문자열 기준 위치는 섹션 시작 + 8 + 문자열 수 * 4. 상대 주소 0도 유효한 첫 문자열.
- 원본의 연속 문자열 풀, 섹션 경계, NUL 종결, 엄격한 디코딩을 검사.
- 줄 순서가 아닌 원본 주소에 대응하는 포인터 슬롯만 수정.
- 짧은 변경은 원래 슬롯에 쓰고 남는 바이트를 0으로 채움.
- 길이 증가분은 기존 도구와 같이 파일 끝에 추가. 헤더/바이트코드/다른 섹션의 위치는 유지.
- 수정하지 않은 문자열 바이트는 재인코딩하지 않고 그대로 보존.
- 이중 언어 TXT는 JPN 전체를 원본과 대조하고, 내용이 있는 KOR만 기존 치환/인코딩 경로에 전달.
- 저장 전 모든 원래 문자열 참조를 다시 따라가 기대한 바이트와 비교.

저장과 검증 한계
- 선택한 입력 전체를 먼저 검사한 뒤 .pending 완성 -> 파일별 교체 순서로 저장.
- 입력 오류, 원본 해시 불일치, 남은 .pending이 있으면 첫 출력 저장 전에 중단.
- 여러 파일 전체가 하나의 원자적 저장은 아님. 디스크 오류/강제 종료 중 발생한 부분 출력은 적용 금지.
- BUILD SUCCEEDED와 종료 코드 0을 확인. 실패하더라도 이전 output이 남아 있을 수 있음.
- 항상 original을 기준으로 빌드. 확장된 output을 새 원본으로 쓰지 말 것.
- 원본 856개, 문자열 108,040개의 구조 검증 및 무수정 바이트 왕복 확인.
- 현재 빌드 815개, 문자열 참조 107,840개를 검사. 기존 번역 2,830항목을 791개 파일의 KOR에 보존.
- 전환 전후 815개 SB 결과 SHA-256이 모두 일치하고, 미번역 전투 TXT 24개는 빈 KOR로 원본 바이트를 유지.
- 전환 자료와 재검증 명령은 codex-lab/sb-bilingual/README.md 및 validation.json에 보존.
- 추가 전투 24개 연결 후 전체 219개 테스트와 아카이브 10,455항목 대조 통과. 실제 BAT 21가지 실행에는 새 전투 TXT 드롭 및 전투 29개 기본 빌드가 포함됨.
- 게임 로더의 확장 문자열 처리, 화면 표시, 제어코드 동작은 아직 게임에서 검증하지 않음.
- 구형 SB 코드는 codex-lab/manual-rebuild/backup-before-folder-workflow에 해시 대조 백업 후 기존 경로에서 제거. 운영 도구는 이 백업을 참조하지 않음.
