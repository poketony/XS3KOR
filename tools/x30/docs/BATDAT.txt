명령 실행 기준: XS3KOR/tools/x30. 일상 작업 순서는 ../README.txt를 참고하세요.
검증 개수와 초기 번역 상태는 구현 당시의 기록이며 현재 결과와 다를 수 있습니다.

X30 batdat 빌드 (2026-10-24)

0.X30/bat/kr/batdatEdit/batdat.json의 ko, ko_name, ko_desc를 편집하고 같은 폴더의 patch.bat를 실행합니다.
검증에 성공하면 같은 폴더에 batdat.bin.new가 생성됩니다. 원본 BIN/JSON과 외부 ROM 폴더는 수정하지 않습니다.
tools/x30의 도구/기준 자료와 위 작업 JSON을 직접 사용합니다. 실제 게임 확인은 하지 않았습니다.

실행
- patch.bat: 전체 검사 후 한 파일 저장. 섹션별 사용량/남은 바이트 표시. 새로 추가했던 중복 Build_batdat.bat는 제거했습니다.
- JSON 하나를 BAT에 드롭하거나 CLI 인자로 주면 해당 파일을 직접 읽습니다. 저장소 0.X30 또는 tools/x30 안의 JSON만 허용합니다.
- CLI 예(저장소 루트): 0.X30\bat\kr\batdatEdit\patch.bat 0.X30\bat\kr\batdatEdit\batdat.json --check
- 상대 경로는 호출 폴더 기준. 누락/잘못된 입력은 오류이며 기본 사본으로 대체하지 않습니다. XS3_NO_PAUSE=1이면 BAT 대기를 생략합니다.
- python -X utf8 -B build_batdat.py --check: 저장 없이 검사와 메모리 내 재구성.
- python -X utf8 -B -m unittest discover -s tests -p test_batdat.py: batdat 전용 회귀 테스트 27개.
- Python 3.10 이상. 추가 패키지나 외부 폴더 불필요.
- 원문 추출: Extract_batdat.batlock을 사용할 때만 .bat로 바꾸고 끝나면 되돌립니다. 원본 BIN에서 일본어 batdat.json을 추출하며 기존 JSON은 절대 덮어쓰지 않습니다.

누락 항목을 포함한 전체 JSON 검토
- 작업 JSON 옆의 Export_batdat.batlock을 .bat로 바꾸어 실행하면 같은 폴더에 batdat.expanded.json을 새로 만듭니다. 기존 파일이 있으면 중단합니다. 사용 후 .batlock으로 되돌립니다.
- 현재 작업 JSON의 번역을 보존하고, 누락됐던 실제 필드를 원문으로 포함한 정상 구조의 검토용 JSON입니다. 게임 BIN을 만들거나 기본 작업 JSON을 교체하지 않습니다.
- Export BAT도 JSON 하나 드롭/CLI 입력을 받습니다. 기본값은 현재 batdat.json입니다.
- 검토용 JSON을 patch.bat에 드롭하면 그 내용으로 시험 빌드할 수 있습니다. 기본 더블클릭 빌드는 계속 기존 작업 JSON을 읽습니다.
- 최종 채택 전에는 별도 작업본을 병행 관리하지 마세요. 검토 후 기본 작업 JSON 교체는 사용자의 선택이며 자동으로 수행하지 않습니다.
- CLI에서 다른 검토 파일명 지정: python -B build_batdat.py --export-editor output/batdat.review2.json

입력과 출처
- 0.X30/bat/kr/batdatEdit/batdat.bin: 직접 읽는 일본판 원본, 127,836바이트. 같은 폴더의 XENOSAGA KOR-JPN.json도 직접 읽고 해시 검증합니다.
- ../../0.X30/bat/kr/batdatEdit/batdat.json: 유일한 기본 작업 입력. 현재의 구형 형식도 엄격히 식별하여 메모리에서만 구조를 바로잡고 번역을 적용.
- reference/batdat.legacy.json: 알려진 구형 구조를 식별하는 해시 검증 기준 자료. 이 파일의 번역문을 작업 입력 대신 사용하지 않음.
- reference/editor-snapshots-20261024/batdat.json: 이전 복구 사본을 보존 이동한 회귀 테스트 자료. 빌드 입력/대체 경로가 아님.
- batdat_sources.json: 출처/해시/빌드 경로.
- batdat_migration.json: 번역 이관, 복구된 필드, 잘못 추출됐던 미번역 필드의 상세 기록.
- 기존 JSON/BIN 내용은 수정하지 않음. 구형 도구는 codex-lab/manual-rebuild/backup-before-folder-workflow에 바이트 대조 백업 후 기존 경로에서 제거. 운영 도구의 백업 참조나 자동 동기화 없음.

확인하고 고친 구조 문제
1. 파티원/에너미 마지막 항목 누락
   이름 포인터는 56바이트 레코드 내부의 +22 위치에 있습니다.
   기존 추출기는 +22를 레코드 테이블 앞의 헤더처럼 빼서 각각 마지막 한 항목을 제외했습니다.
   파티원 17개/에너미 177개가 맞으며, 빠졌던 予備와 SKJ_008을 원문으로 복구했습니다.
   이름 다음 2바이트는 스탯 값이므로 수정하지 않습니다. JSON의 기존 end_ptr 키는 호환을 위해 유지한 읽기 전용 값입니다.
2. TEC 1 레코드 간격
   실제 간격은 20바이트, 128항목입니다. 기존 28바이트/91항목은 숫자 필드를 문자열 포인터로 오인했습니다.
   잘못 추출된 144개 필드에는 기존 번역이 없음을 확인하고 메모리상의 복구 문서에서 제외합니다. 해당 가짜 필드에 새 번역이 있으면 손실을 막기 위해 오류로 중단합니다.
   실제 문자열을 엄격한 EUC-JIS-2004로 다시 읽어 복구했습니다. 기존 미번역 원문을 임의로 번역하지 않았습니다.
3. 콤보/설명 1의 두 번째 포인터
   이름 다음 값은 빈 설명 문자열을 가리키는 유효한 포인터입니다.
   총 48개 빈 설명을 모델에 포함하여 이름을 재배치할 때 함께 갱신합니다.
   이 두 섹션은 ko 대신 ko_name/ko_desc 형식이 되었으며 기존 ko는 ko_name으로 그대로 옮겼습니다.
4. TEC 2 용량 초과
   현재의 ＶＢ−아침놀 번역을 포함하면 문자열 풀이 8,709바이트로 원래 용량보다 1바이트 큽니다.
   기존 도구는 TEC 2 전체를 적용하지 않은 채 다른 섹션의 결과를 저장했습니다.
   새 도구는 번역을 줄이지 않고 완전히 같은 이름/설명 쌍 4건을 한 쌍으로 공유하여 9바이트를 절약합니다.
   결과는 8,700/8,708바이트, 여유 8바이트입니다. 이름 바로 다음에 설명이 오는 배치도 유지합니다.

편집 규칙
- ko/ko_name/ko_desc의 값만 수정. jp 계열, idx, 포인터, 섹션 메타데이터는 원본과 일치해야 함.
- JSON 섹션/항목 순서는 바꿀 수 있으나 ID 누락/중복/알 수 없는 ID나 필드는 오류.
- JSON 객체의 중복 키도 오류. 마지막 값만 조용히 사용하는 처리를 하지 않음.
- 빈 문자열은 명시적인 삭제. 키 자체가 빠지면 오류이며 원문으로 자동 대체하지 않음.
- 한글 -> XENOSAGA KOR-JPN.json의 대응 한자 -> EUC-JIS-2004 방식 유지.
- 문장 부호, 제어코드, 공백, 개행은 임의로 정규화하지 않음. JSON의 이스케이프 규칙을 따를 것.
- 기존과 같이 문자열 끝의 [menu_sita]만 처리: 공백 -> 、, @ -> 반각 공백.
- 인코딩 불가 문자를 ?로 바꾸거나 삭제하지 않음. NUL 삽입도 오류.
- 알려진 구형 JSON은 메타데이터/원문/포인터가 기준 자료와 정확히 일치할 때만 메모리에서 정규화합니다. ko 계열의 새 번역은 실제 포인터로 연결합니다.
- 정상 구조 JSON도 입력할 수 있습니다. 임의로 바꾼 메타데이터, 알 수 없는 구조, 중복 ID를 자동 복구하지 않습니다.
- 현재 구형 작업 JSON에 없는 복구 필드는 원문으로 유지됩니다. 실제 작업 JSON의 확장/교체는 별도 승인 전까지 하지 않습니다.

저장 방식
- 섹션 크기, 파일 크기, 헤더의 섹션 시작 위치를 유지.
- 바뀐 섹션의 문자열 풀과 구조로 확인한 2바이트 포인터만 재구성. 스탯과 나머지 8개 섹션은 보존.
- 수정하지 않은 섹션은 바이트 그대로 유지. 변경 없는 문자열도 원본 바이트를 보존.
- 일반 재구성이 용량에 들어가면 공유하지 않음. 초과 시에만 완전히 같은 레코드의 문자열 묶음을 공유.
- 공유해도 넘치면 전체 빌드 실패. 일부 섹션만 적용한 결과를 저장하지 않음.
- 모든 입력과 3,040개 결과 참조를 검증한 뒤 .pending 파일을 완성하여 기존 출력과 교체.
- 실패해도 이전 output은 남아 있을 수 있음. BUILD SUCCEEDED/종료 코드 0이 아닌 실행의 결과는 적용 금지.
- 남아 있는 .pending은 중단 흔적이므로 자동 삭제하거나 덮어쓰지 않음.
- original을 기준으로 반복 빌드. 재배치/공유된 output을 새 원본으로 사용하지 말 것.

검증 범위와 한계
- 텍스트 20개 섹션, 1,972항목, 3,040필드. 원본의 문자열 풀 전체를 구조 기반 참조와 대조.
- 기존 번역 1,005개 보존. 실제 필드 268개 복구, 번역이 없던 잘못된 필드 144개 제외.
- 무편집 왕복은 원본과 바이트 일치. 현재 빌드는 크기/헤더/스탯/비텍스트 영역 보존.
- 작업 JSON 직접 읽기로 전환한 결과는 이전 복구 사본의 검증 결과와 바이트 일치. 전환 전후 기존 작업 JSON 불변.
- 전용 27개 및 SB/batdat 수동 입력/비파괴 내보내기/누락 범위 21개 테스트가 있음. 실제 batdat BAT 5가지 실행, 기존 patch.bat 호출과 내보내기/검토 JSON BAT 4가지 실행 검증 통과.
- 기존 도구와의 차이는 파티원, 에너미, 콤보, 설명 1, TEC 2의 다섯 섹션으로 제한됨.
- 게임이 공유 문자열을 수정하지 않는다는 가정으로 동일 문자열 쌍 공유를 사용함.
  참조가 가리키는 바이트는 모두 검사했지만, 공유 동작과 화면 표시/제어코드 처리는 실제 게임 확인이 필요함.
- 여유가 적은 에테르 1(7B), 도구(8B), 에테르 3(10B), 설명 2(19B) 등은 후속 번역 시 다시 용량 검사 필요.
- 이 절은 batdat 검증 범위입니다. 현재 다른 포맷과 폴더별 작업 구조는 ../README.txt 및 ARCHIVE.txt를 참고하세요. ROM 적용과 게임 화면 검증은 별도입니다.
